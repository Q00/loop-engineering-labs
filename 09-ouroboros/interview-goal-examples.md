# 실습용 goal 예시 다섯 개

`ooo interview start`에 넣을 한 줄이다. **자기 업무 아이디어가 있으면 그걸 쓰는 게 먼저다.** 떠오르지 않을 때만 아래에서 하나 고른다.

고르는 기준은 셋. 실습장에서 한 바퀴 도는 데 무리가 없어야 한다.

- **로컬에서 끝난다** — 배포·외부 API 키·사내 시스템 접근이 필요 없다
- **되돌리기 싸다** — 실패해도 파일 몇 개 지우면 원상복구
- **완료를 눈으로 확인할 수 있다** — STEP 5의 `ooo qa`에 걸 합격 기준을 한 문장으로 쓸 수 있다

---

```
커밋 로그로 주간 배포 노트 초안을 만드는 CLI
```
덱에서 쓰는 예시. `git log`를 읽어 날짜 구간별로 묶고 마크다운 초안을 뱉는다.
`ooo qa` 합격 기준 예: "항목마다 커밋 해시와 영향 범위가 있고, 내부 용어에 설명이 붙어 있는가."

```
CSV 파일을 받아 컬럼별 결측치와 이상치를 표로 요약해 주는 CLI
```
입력 파일 하나, 출력 표 하나. 판정이 명확하다.
합격 기준 예: "컬럼마다 결측 비율과 범위를 벗어난 값의 개수가 표에 있는가."

```
폴더 안 마크다운 문서들의 깨진 상대 링크를 찾아 목록으로 뽑는 CLI
```
읽기 전용이라 되돌릴 것 자체가 없다. 첫 실습으로 가장 안전하다.
합격 기준 예: "깨진 링크마다 파일 경로와 줄 번호가 나오는가."

```
회의록 텍스트에서 액션 아이템만 담당자와 함께 뽑아 주는 스크립트
```
`ooo qa --artifact-type document`를 써 보기 좋은 과제.
합격 기준 예: "액션 아이템마다 담당자가 붙어 있고, 담당자가 불분명한 항목은 따로 표시되는가."

```
프로젝트 폴더의 의존성 목록을 읽어 라이선스별로 묶어 정리하는 CLI
```
입력이 이미 있는 파일(`package.json`, `requirements.txt` 등)이라 준비물이 없다.
합격 기준 예: "패키지마다 라이선스가 붙어 있고, 확인 불가한 것은 별도 구획에 모였는가."

## 인터뷰가 물어 올 것

무엇을 고르든 인터뷰는 대략 이런 걸 되묻는다. 미리 답을 정해 둘 필요는 없다 — **답이 없다는 걸 발견하는 게** 이 단계의 목적이다.

- 입력은 어디서 오고, 출력은 어디로 가나
- 하지 **않을** 일은 무엇인가 (`Non-goal:` 줄이 될 부분)
- 무엇을 보면 "됐다"고 말할 수 있나 (`acceptance_criteria`가 될 부분)
- 실패했을 때 무엇을 보여 줘야 하나
