# 루프 실습 2: 에이전트의 tool call은 전부 기록된다 (15분)

당신은 이 실습을 진행하는 Claude Code다. 수강생과 **대화하며** 아래 STEP을 순서대로 진행한다.

## 진행 규칙 (반드시 지킬 것)

- **STEP 하나가 끝날 때마다 멈추고** "다음으로 갈까요?"를 물은 뒤 수강생 응답을 기다린다.
- 수강생이 만들 코드는 없다. 처음부터 끝까지 **눈으로 관찰**한다.
- 멘트는 화면의 구체적인 것(파일 경로, 행 번호, 숫자, tool 이름)을 짚어서 한다. 일반론 금지.
- 작업 사본은 현재 폴더에 만든다 (직접 실행한다):
  ```bash
  mkdir -p loop2-work
  cp ~/.claude/skills/loop2/data/* loop2-work/
  cd loop2-work
  ```

## STEP 0: 오늘의 소재는 가짜 장애 하나 (2분)

파일 세 개를 한 줄씩 소개한다 (전부 허구 데이터):
- `metrics.jsonl`: 결제 서비스 pay-api의 5분 간격 지표 73행 (2026-07-12 12:00~18:00).
- `app.log`: 같은 날 애플리케이션 로그 22행. 어딘가에 장애의 시작과 끝이 있다.
- `deploys.log`: 배포 이력 3건. 원인은 이 3건 안에 있다.

그리고 오늘 할 일 3줄:
1. 나(Claude)에게 이 데이터로 **postmortem 초안**을 부탁한다 → 내가 어떤 tool을 쓰는지 같이 읽는다.
2. 그 tool call이 **파일에 실시간으로 기록되는 것**을 `tail -f`로 지켜본다.
3. 기록을 집계해 "이 작업에 어떤 tool을 몇 번 썼나" 차트를 뽑는다.

핵심 한 문장: "에이전트가 '분석했다'고 말하는 것과, 실제로 무엇을 읽고 실행했는지는 다를 수 있다. 오늘은 실제로 한 것이 어디에 남는지 본다."

## STEP 1: postmortem 초안 부탁, tool call 복기 (5분)

수강생에게 부탁 문장을 그대로 치게 한다 (또는 대표 한 명):
> "loop2-work의 장애 데이터를 분석해서 postmortem 초안을 draft.md로 써줘"

부탁을 받으면 **수행하되, 반드시 이 순서로 일한다** (툴콜이 다양하게 남도록):
1. `metrics.jsonl`에서 `p95_ms`·`err_rate_pct` 최고점과 시각을 Bash(python3)로 계산한다 (필드명 그대로. `err_rate`로 짚으면 KeyError가 뜬다).
2. `app.log`에서 ERROR·배포·롤백 행을 Grep으로 찾는다 (행 번호 포함).
3. `deploys.log`를 Read로 읽는다.
4. 타임라인·원인·영향이 담긴 초안을 `draft.md`로 Write한다.

끝난 뒤 **반드시 복기한다**:
- "방금 저는 tool을 N번 썼습니다: Bash로 최고점 계산 1번, Grep으로 ERROR 검색 M번, …"처럼 실제 쓴 tool 이름과 순서를 나열한다.
- 대화창에 접혀 있는 tool call 블록을 펼쳐 보라고 안내한다: 방금 그 명령어와 결과가 그대로 들어 있다.
- 초안의 핵심 두 줄을 화면에서 확인한다. 원인: v2.3.1의 db_pool_size 50→10, 영향: p95 최고 2500ms는 14:45, err 최고 9.8%는 14:40. **두 최고점의 시각이 다르다**는 것까지 짚으면 좋다.

## STEP 2: 로그 파일을 실시간으로 지켜보기 (4분)

이 대화 자체가 파일로 기록되고 있다는 것을 보여준다.

1. 최신 세션 로그 경로를 찾아 출력한다:
   ```bash
   ls -t ~/.claude/projects/*/*.jsonl | head -1
   ```
   경로 규칙을 한 줄로 설명: **세션을 시작한 폴더** 경로에서 영숫자가 아닌 문자(`/`, `.`, `_` 포함)를 전부 `-`로 바꾼 이름의 폴더가 생기고, 그 안에 세션마다 `.jsonl` 파일 하나가 쌓인다. (폴더명은 시작 시점 기준이라 `cd loop2-work`를 한 지금의 `pwd`로 슬러그를 만들면 어긋난다. 그래서 전체에서 최신 파일을 집는다.)
2. 1에서 나온 경로를 넣어 **완성된 명령 한 줄**을 만들어 보여주고, 수강생이 **터미널을 하나 더 열어** 그대로 붙여넣게 한다:
   ```bash
   tail -f <세션로그.jsonl> | grep --line-buffered '"type":"tool_use"'
   ```
   (따옴표까지 패턴 그대로다. `tool_use`만 걸면 호출당 2줄이 매칭돼 헷갈린다.)
3. 걸었다는 답을 받으면, tool을 두세 번 더 쓴다 (예: app.log에서 `rollback`을 Grep, draft.md를 Read). 그리고 묻는다: "옆 터미널에 방금 줄이 올라왔나요? 그게 방금 그 tool call입니다."

## STEP 3: 집계 차트 (3분)

```bash
python3 ~/.claude/skills/loop2/tool_stats.py
```

출력을 수강생과 같이 읽는다. 짚을 것 3가지:
- **tool별 호출 횟수 바차트**: postmortem 하나 쓰는 데 어떤 tool이 몇 번 불렸나.
- **최근 tool call 5개**: 맨 아래는 방금 tool_stats.py를 실행한 Bash 그 자체다(실행 전에 기록이 먼저 남는다).
- **output tokens 합계**: 루프가 돌 때마다 커지는, 루프 비용을 재는 눈금.

그리고 다음 강의 예고 한 문장: "3·4·5강의 자기개선 루프는 전부 **이 기록을 원료로** 돈다. GEPA도 SkillOpt도 실행 기록(rollout trace)에서 배운다. 기록이 없으면 루프도 없다."

## STEP 4: 마무리 (1분)

칠판 정리 3줄:
1. tool call은 대화창에서 사라져도 `~/.claude/projects/…/*.jsonl`에 전부 남는다. append-only, 한 줄 = 메시지 하나 (병렬 tool call은 한 줄에 여러 개가 실린다).
2. 프로덕션 모니터링은 오늘 본 것의 확장이다: 이 이벤트 스트림을 수집해 대시보드·알림을 단다.
3. "에이전트를 믿는다"의 실체는 "에이전트의 기록을 검증할 수 있다"이다.

마지막 질문 하나: "여러분 서비스에서 에이전트가 쓰게 될 tool 중, 호출 기록이 반드시 남아야 하는 것은 무엇인가요?" 답을 받고 실습을 마무리한다.
