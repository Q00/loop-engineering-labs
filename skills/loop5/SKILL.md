# 루프 실습 5: 보고서가 검문을 통과할 때까지 (15분)

당신은 이 실습을 진행하는 Claude Code다. 수강생과 **대화하며** 아래 STEP을 순서대로 진행한다.
4강 루프는 **지시서를 깎는 학습 루프**였다(다음 실행이 좋아진다). 오늘은 **산출물을 깎는 수렴 루프**다(이번 보고서가 좋아진다).
검문관은 LLM이 아니라 프로그램이다. 과정과 산출을 규칙으로 검증하는 VPRM(Verifiable Process Reward Models) 계열에서 빌린 발상이다.

## 진행 규칙 (반드시 지킬 것)

- **STEP 하나가 끝날 때마다 멈추고** 수강생 확인을 받은 뒤 진행한다.
- 합격 판정은 **반드시 `python3 verify.py report.md`의 출력만** 근거로 삼는다.
- **STEP 1이 끝나기 전에는 RULES.md도, verify.py도 열지 않는다.** verify.py 안에 규정이 코드로 다 들어 있다. 열면 규정을 모르는 초안이라는 첫 관찰이 성립하지 않는다. STEP 0의 검문기 소개는 이 SKILL.md의 문장만으로 한다.
- cd가 유지되지 않는 환경이면 명령마다 작업 폴더 절대경로를 붙인다 (`cd <작업폴더> && python3 verify.py report.md`).
- **강의 전 준비 (규정 7용)**: `~/.claude/settings.json`에 `"showThinkingSummaries": true`가 있어야 하고,
  **그 뒤에 연 세션**이어야 한다. 기본값이 false라 사고 요약이 안 내려온다. 확인:
  `python3 -c "import json,os;print(json.load(open(os.path.expanduser('~/.claude/settings.json'))).get('showThinkingSummaries'))"`
  꺼져 있으면 규정 7은 위반이 아니라 건너뛰기로 처리되니 실습 자체는 굴러간다.
- 작업 사본 (직접 실행한다):
  ```bash
  mkdir -p loop5-work && cp -R ~/.claude/skills/loop5/{RULES.md,verify.py,trace_read.py,data} loop5-work/ && cd loop5-work
  ```

## STEP 0: 재료 소개 (1분)

세 파일 소개:
- `data/`: 2강부터 함께한 그 장애 (pay-api, 2026-07-12).
- `RULES.md`: 보고서 규정. **아직 열지 않는다.**
- `verify.py`: 규정을 그대로 코드로 옮긴 검문기. 특징 두 가지를 예고한다: **인용문을 원본 로그 행과 문자열 대조**하고, **수치를 metrics.jsonl에서 직접 계산해 대조**한다. "제가 그럴듯하게 지어내면, 이 프로그램에 걸립니다."

## STEP 1: 규정을 모르는 초안 (3분)

RULES.md를 열지 않은 채, 데이터만 보고 평소 하던 방식으로 장애 보고서를 `report.md`로 쓴다.
그리고 첫 검문:
```bash
python3 verify.py report.md
```
FAIL과 위반 리스트가 나온다 (형식 규정을 몰랐으므로 보통 4건 이상). 위반 줄을 수강생과 하나씩 읽는다. "잘 쓴 보고서"와 "검문을 통과하는 보고서"가 다르다는 것을 짚는다.

## STEP 2: 수렴 루프 (3분 30초)

이제 RULES.md를 열어 5조를 같이 읽는다. 그리고 루프를 돈다:

1. **한 라운드에 한 규정 분량만** 고친다 (위반 리스트의 같은 [규정N] 묶음 하나). 전면 재작성 금지. 성실하게 다 고치면 한 방에 끝나 버려서 수렴이 안 보인다. 위반 수가 계단으로 줄어드는 것이 이 STEP의 관찰 대상이다.
2. `python3 verify.py report.md` 재검문.
3. 위반 수를 한 줄로 중계한다: "4건 → 2건 → 1건 → 0건". 0건(PASS)까지 반복한다.

PASS가 나오면 초록 PASS 줄을 같이 확인하고, 바로 백업해 둔다: `cp report.md report.pass.bak` (STEP 3에서 쓴다).

## STEP 3: 환각은 검문에 걸린다 (2분 30초)

PASS 상태에서 일부러 오염시켜 본다. 수강생에게 예고하고 (`report.pass.bak` 백업이 있는지 먼저 확인):

1. report.md의 인용 하나를 **그럴듯한 가짜**로 바꾼다. 예: 행 번호를 `[app.log:99]`로 (22행뿐인 로그), 또는 인용문 끝에 짧은 지어낸 구절을 덧붙인다 (위반 메시지가 40자에서 잘리니 오염 문구는 짧게).
2. 수치 하나도 바꾼다: `p95 최고 2500ms`를 `3100ms`로.
3. `python3 verify.py report.md` → FAIL 두 건. 위반 메시지를 소리 내어 읽는다: "존재하지 않는 행", "실측은 2500ms".

멘트: "방금 넣은 게 환각입니다. 그럴듯하고, 문장도 매끄럽고, 틀렸습니다. LLM 검토자는 이걸 통과시킬 수 있습니다. 원본과 대조하는 코드는 통과시키지 않습니다."
`cp report.pass.bak report.md`로 복원하고 PASS를 다시 확인한다.

## STEP 3.5: 산출물만 보는 검문의 한계 (2분)

여기서 2강의 그 세션 로그가 재료로 들어온다. 지금까지 검문기는 **완성된 보고서만** 봤다. 어떻게 썼는지는 안 봤다.

1. 방금 보고서를 손질한 구간을 잘라 볼 마커를 만든다:
   ```bash
   touch mark.txt
   ```
2. 마커 이후의 행동만 기준으로 과정 검증을 켜서 재검문한다:
   ```bash
   python3 verify.py report.md data --trace mark.txt
   ```
   헤더가 `검문 7종, 산출물과 과정을 함께`로 바뀌고 **규정 6에서 FAIL 2건**이 뜬다. 인용도 수치도 원본과 일치하는데 걸린다.
   ```
   X  [규정6] app.log을 인용·대조했는데 이번 라운드에 연 기록이 없다
   X  [규정6] metrics.jsonl을 인용·대조했는데 이번 라운드에 연 기록이 없다
   ```
   규정 7이 0~2건 더 붙을 수 있다. 사고 요약에 파일명이 나왔는지에 달렸고, 요약은 매번 다르다.
   **이 흔들림 자체가 STEP 3.6의 재료다.** 몇 건이 나오든 당황하지 말고 그대로 읽는다.
3. 이제 원본을 실제로 다시 열고 재검문하면 PASS다.
   ```bash
   grep -c ERROR data/app.log
   head -3 data/metrics.jsonl
   python3 verify.py report.md data --trace mark.txt
   ```
   읽기는 `grep`·`head`처럼 **읽기 명령 자체로 시작**해야 기록에 남는다. 앞에 `time`·`LC_ALL=C`가 붙는 정도는 괜찮지만, 함수나 스크립트 안에서 읽으면 판독기가 못 본다.

규정 6이 엉뚱하게 전부 위반으로 나오면 원본을 안 읽은 게 아니라 **세션 로그를 잘못 골랐을** 가능성이 높다. `python3 trace_read.py --since mark.txt --touched`로 첫 줄 경로가 지금 세션인지, tool call이 0개인지 확인한다. 이 실습을 서브에이전트에 위임해도 같은 증상이 나온다 (자식 기록은 세션 로그에 안 남는다).

멘트: "규정 1~5는 산출물을 봤습니다. 통과했죠. 규정 6은 2강에서 본 그 세션 로그를 열어 **정말 원본을 보고 썼는지**를 봅니다. 남이 쓴 보고서를 이어받아 고칠 때, 인용을 그대로 두고 원본은 확인하지 않는 일이 실무에서 제일 흔합니다. 산출물만 보는 검문은 그걸 못 잡습니다."

이게 VPRM의 P, 즉 **과정(Process) 검증**이다. 결과가 맞았는지가 아니라 어떻게 도달했는지를 규칙으로 본다.

## STEP 3.6: 사고까지 볼 수 있나 (1분 30초)

규정 6은 **행동**을 봤다. 그럼 **사고**는 볼 수 있나. 재료를 먼저 꺼내 보여 준다:

```bash
python3 trace_read.py --since mark.txt --thinking
```

방금 구간의 사고 요약이 몇 줄 뜬다. 규정 7은 이걸 재료로 **근거로 쓴 파일 이름이 사고에도 나오는지**만 본다.
파일명이 어디든 한 번 나오면 통과하는, 일부러 느슨한 규정이다.

여기서 반드시 짚을 것이 두 가지다.

1. **이건 원본 사고가 아니라 요약이다.** 원본은 암호화되어 세션 로그의 `signature` 안에만 있고,
   복호화 키는 Anthropic이 갖고 있다. 손에 잡히는 증거로 보여 주려면 signature 길이를 재 본다:
   ```bash
   python3 -c "import glob,os,json;p=max(glob.glob(os.path.expanduser('~/.claude/projects/*/*.jsonl')),key=os.path.getmtime);L=[len(b.get('signature') or '') for l in open(p) for b in ((json.loads(l).get('message') or {}).get('content') or []) if isinstance(b,dict) and b.get('type')=='thinking'];print('사고 블록',len(L),'signature 길이',min(L or [0]),'~',max(L or [0]))"
   ```
   길이가 제각각인 건 해시가 아니라 **사고 길이에 비례하는 암호문**이기 때문이다.
   그리고 기본값이 `display: "omitted"`라, 옵션을 켜지 않으면 요약조차 안 내려온다(그때 규정 7은 건너뛴다).
2. **그래서 규정 7의 PASS는 약하다.** "사고가 검증됐다"가 아니라 "자기 요약과 보고서가 어긋나지 않는다"까지다.
   규정 3·4는 원본과 대조했지만, 규정 7이 대조하는 건 **모델의 자기 보고**다. 대조할 원본이 없다.

멘트: "규정 3은 원본 로그와 대조했습니다. 규정 6은 실제 행동 기록과 대조했습니다.
규정 7은 대조할 원본이 없습니다. 모델이 스스로 요약한 말과 맞춰 볼 뿐입니다.
**검증의 강도는 대조할 원본이 얼마나 단단하냐로 결정됩니다.** 원본 → 행동 → 자기 보고 순으로 약해집니다."

## STEP 4: 마무리 (1분)

칠판 정리 3줄:
1. 4강은 지시서를 깎았고(학습 루프, 내일도 쓴다), 오늘은 산출물을 깎았다(수렴 루프, 이번 것을 끝까지). 실무 루프는 이 둘의 조합이다.
2. 검문이 코드면 루프는 **밤에도 혼자 돈다**. 사람 검토는 PASS된 것 위에서 시작하면 된다. **PASS는 하한선이다**: 검문기는 규정에 적힌 것만 보고, 규정 밖 오류는 그대로 통과한다. 그래서 사람 검토는 없어지지 않고, 규정 밖 내용과 판단으로 올라간다.
3. 환각 대책은 더 좋은 모델이 아니다. **대조할 원본이 있어야 환각이 잡힌다**. 인용에 행 번호를 강제한 이유다.
4. 규정 1~5는 산출물을, 규정 6은 과정을 봤다. **과정 검증의 재료가 2강에서 관찰한 그 tool call 기록이다.** 기록이 없으면 규정 6을 만들 수조차 없다.
5. 규정 7은 사고까지 가 봤지만, 거기서 검증은 **자기 보고 대조**로 약해진다. 원본 → 행동 → 자기 보고 순으로 단단함이 떨어진다. 루프를 설계할 때는 **제일 단단한 원본이 있는 자리부터** 규정을 건다.

마지막 질문: "여러분이 매주 만드는 산출물 중, verify.py처럼 원본 대조가 가능한 것은 무엇인가요?" 답을 받고 닫는다.

## 예상 질문 대응

- "명령만 치면 통과하는 거 아닌가요?": 맞다. 정직하게 인정하고 재료로 쓴다. "규정 6은 로그에 남은 **명령**을 봅니다. 없는 경로로 `grep`을 쳐서 실패해도 통과합니다. 이것도 하한선입니다. 더 엄격하게 하려면 읽기가 성공했는지, 인용한 그 행이 출력에 있었는지까지 봐야 합니다. 규정을 얼마나 촘촘히 만들지가 곧 이 루프를 얼마나 신뢰할지입니다."
- "검문만 통과하면 다 맞는 건가요?": 정직하게 답한다. "아니요. 검문기는 규정에 적힌 것만 봅니다. 최고값이 아닌 수치나 서술의 사실관계는 규정 밖이라 통과합니다. PASS는 '규정 위반 없음'이지 '전부 검증됨'이 아닙니다. 그래서 규정을 늘려 가면 이 루프도 그만큼 커집니다."
- "규정이 너무 빡빡한 것 아닌가요?": "빡빡한 게 아니라 **검증 가능**한 겁니다. '보고서를 잘 써라'는 자동화가 안 되지만 '인용은 행 번호와 함께'는 됩니다. 루프에 태울 수 있는 기준만 자동으로 돌고, 나머지는 사람 몫으로 남습니다."
- "저건 진짜 사고인가요?": 아니다. 정직하게 답한다. "모델이 스스로 요약한 사고입니다. 원본은 암호화돼 signature에만 있고 키는 우리에게 없습니다. 그래서 규정 7은 규정 3보다 약한 검문이고, 저는 그걸 알고 느슨하게 걸었습니다. 사고를 정말 검증하고 싶으면 방법은 하나입니다. **사고를 산출물로 꺼내게 하는 것**입니다. 근거를 파일에 쓰게 하면 그때부터는 원본 대조가 가능해집니다."
- "규정 7이 어떤 날은 걸리고 어떤 날은 안 걸리는데요?": 맞다. "요약은 매번 다르게 나옵니다. 규정 3·4는 몇 번을 돌려도 같은 답이 나오지만 규정 7은 아닙니다. **검문기 안에 결정적인 규정과 그렇지 않은 규정이 섞여 있으면, 그렇지 않은 쪽이 루프 전체의 신뢰도를 정합니다.** 그래서 실무에선 이런 규정을 게이트가 아니라 경고로 둡니다."
- "실무 데이터는 이렇게 깨끗하지 않은데요?": 정직하게 답한다. "맞습니다. 오늘 데이터는 검문이 성립하도록 만든 교보재입니다. 실무에선 검문기 만들기가 일의 절반이고, 그 절반이 곧 이 코스가 말하는 loop engineering입니다."
